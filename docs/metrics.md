# Measurement design: questions, SLIs, SLOs, metric catalog (MET-01, Annex II)

All definitions here are implemented as code:
- recording rules and alerts: `k8s/observability/rules/pfd-slo-rules.yaml` (generated by `scripts/gen-slo-rules.py`)
- dashboard: `k8s/observability/dashboards/pfd-overview.json` (generated by `scripts/gen-dashboard.py`)
- Grafana → folder **PFD** → *PFD · Event ingestion overview* (environment selector: `pfd-prod` / `pfd-dev`)

## 1. Operational questions

| # | Question | Decisions it supports | Answered by |
|---|---|---|---|
| Q1 | **Is ingestion healthy for clients?** Are valid events accepted quickly and without server errors? | Roll back a release, scale the API, investigate a misbehaving client (rejection spike) | Availability and latency SLIs; outcome, rejection and status-code panels |
| Q2 | **Does processing keep up with ingestion?** How much backlog and delay does a capacity reduction cause? *(course-suggested question for Scenario 3)* | Add processor replicas or batch size, judge the impact of an incident, decide whether a backlog will drain on its own | Freshness SLI; accepted vs processed rate; backlog; wait vs processing time |
| Q3 | **Is there enough capacity, and what limits it?** | Adjust requests/limits, resize the VM, find the bottleneck (CPU, memory, DB) | CPU/memory vs requests/limits, node utilisation, restarts |

## 2. SLIs

All SLIs are computed per environment (`namespace` label) from application metrics scraped every 15 s.

| | SLI 1: Ingestion availability | SLI 2: Processing freshness *(scenario-specific)* | SLI 3: Ingestion latency |
|---|---|---|---|
| **Event population** | HTTP requests to `/v1/events` and `/v1/events/batch` | Events that finished processing (`processed` or `failed`) | HTTP requests to `/v1/events*` |
| **Good event** | Status is not 5xx | `processed_at - received_at` ≤ 5 s | Server-side duration ≤ 250 ms |
| **Formula** | 1 − 5xx / total | `lag_bucket{le="5.0"}` / `lag_count` | `duration_bucket{le="0.25"}` / `duration_count` |
| **Unit** | ratio (0–1) | ratio (0–1) | ratio (0–1) |
| **Windows** | 5m, 30m, 1h, 6h (alerting); 7d (SLO) | same | same |
| **Source** | `http_request_duration_seconds_count` (ingest-api) | `event_processing_lag_seconds` histogram (processor) | `http_request_duration_seconds_bucket` (ingest-api) |
| **Exclusions** | 4xx count as good: the service answered correctly (bad key, invalid event, unknown device). Health and metrics endpoints are excluded. | Events still pending are not counted until processed; a stalled processor is covered by the `PfdProcessorStalled` alert, not this SLI. | Network time between client and ingress is not included (server-side measure). |
| **Recording rules** | `pfd:sli_availability:error_ratio_rate{5m,30m,1h,6h,7d}` | `pfd:sli_freshness:error_ratio_rate{…}` | `pfd:sli_latency:good_ratio_rate{…}` |

Why 5 s: the processor polls every 500 ms and handles batches of 100 in under 100 ms (p95 processing ≈ 0.09 s
observed), so in steady state lag is far below 1 s. Five seconds leaves room for bursts while still catching a
slowed or stopped processor within minutes. It is also an exact histogram bucket boundary, so the SLI isn't interpolated.

## 3. SLOs and error budgets

| SLO | Target | Evaluation window | Error budget | In absolute terms |
|---|---|---|---|---|
| **SLO 1: Availability** | 99.5% of ingestion requests are not 5xx | rolling 7 days | 0.5% of requests | at the P3-2 reference load (20 req/s), 0.5% of 12.1 M weekly requests ≈ **60,480 failed requests/week** |
| **SLO 2: Freshness** | 99% of processed events finish within 5 s of receipt | rolling 7 days | 1% of events | at 20 events/s ≈ **120,960 late events/week**, or about **1h40m** of complete processing outage per week |

No SLO is set for latency (SLI 3); it is tracked on the dashboard. The course requires two SLOs, and latency at
the ingress is dominated by client network distance, which we don't control.

- **Budget remaining:** `pfd:slo_*:error_budget_remaining = 1 − (error ratio over 7d / allowed error ratio)`. 1 = untouched, 0 = exhausted, < 0 = SLO breached.
- **Why 7 days:** the project lasts weeks, not months. The course allows test windows, and the same rules
  work with a 30-day window by changing `WINDOWS` in the generator.
- **Justification:** a single VM with no HA (allowed by the course) can't credibly promise 99.9%. One planned
  reboot per week (~2 min) uses ~2% of the availability budget, so 99.5% leaves room for deploys and demos while still making a
  real outage visible.
- **No traffic:** with zero requests the ratio is 0/0 and the panels show "no traffic". That is not counted as good or bad.

## 4. Alerts (Annex II item 7)

| Alert | Type | Condition | For | Why this threshold | Possible false positives |
|---|---|---|---|---|---|
| `PfdIngestAvailabilityBurnRate` | SLO burn | 5xx ratio > 7.2% (14.4 × 0.5%) over **both** 1h and 5m | 1m | 14.4× burn = 1 h consumes ~8.6% of the weekly budget (multi-window pattern, Google SRE Workbook). The 5m window makes it clear quickly after mitigation. | Very low traffic: 1 failure out of 10 requests is 10%. Mitigation: dev traffic is near zero most of the time; treat dev alerts as informational. |
| `PfdFreshnessBurnRate` | SLO burn | late-event ratio > 14.4% over both 1h and 5m | 1m | Same burn-rate reasoning with a 1% budget | A legitimate burst far above capacity (e.g. 10× load test) fires it. That is intended: it is real budget burn. |
| `PfdEventBacklogGrowing` | symptom | pending > 200 **and** rising (deriv over 5m > 0) | 5m | 200 pending ≈ 10 s of input at the reference rate. Rising for 5 min means processing is below ingestion, not a transient burst | A long burst test can fire it while capacity is fine. Check the processed rate before acting. |
| `PfdProcessorStalled` | symptom | pending > 0 and processed rate = 0 for 5m | 3m | Catches a stopped or hung processor even at low traffic, where freshness has nothing to measure | During a planned `replicas=0` (P3-4 test) it fires by design. |

Alertmanager groups alerts by `alertname, namespace` and shows them in its UI and on the dashboard ("Active alerts").
No external notification channel is configured, which keeps it free. A receiver can be added in `k8s/observability/kube-prometheus-stack.yaml`.
Runbooks: `docs/runbooks/alerts.md`.

## 5. Metric catalog

| Metric | Type | Unit | Labels | Source | Calculation / use | Purpose |
|---|---|---|---|---|---|---|
| `events_received_total` | counter | events | `outcome` = accepted/duplicate/rejected | ingest-api | `rate()` per outcome. Invariant: received = accepted + duplicate + rejected | Q1 throughput, duplicate handling (ESC3-05, ESC3-09) |
| `events_rejected_total` | counter | events | `reason` (bounded enum, 10 values) | ingest-api | `rate()` by reason | Q1 client/data quality (ESC3-03) |
| `events_processed_total` | counter | events | `result` = processed/failed | processor | `rate()`; compared with the accepted rate | Q2 throughput **(outcome metric)** |
| `events_backlog` | gauge | events | `status` = pending/processing | DB count polled every 5 s | `max by (namespace,status)` (both apps export it) | Q2 backlog |
| `event_processing_lag_seconds` | histogram | seconds | none | processor | `processed_at − received_at` = queue wait + processing. Buckets 0.01…3600 | Q2 delay **(latency/wait metric)**, SLI 2 |
| `event_processing_duration_seconds` | histogram | seconds | none | processor | Effective work per event | Q2: separate waiting from working |
| `http_request_duration_seconds` | histogram | seconds | `method`, `route` (template), `status_code` | ingest-api, processor | Percentiles, SLI 1 and SLI 3. Buckets 5 ms…10 s | Q1 latency and errors |
| `business_alerts_total` | counter | alerts | `metric` = temperature/humidity | processor | `rate()` | Business view (ESC3-07) |
| `container_cpu_usage_seconds_total` | counter | CPU-seconds | `pod`, `container` | cAdvisor (kubelet) | `rate()` vs `kube_pod_container_resource_requests` | Q3: justify requests (DEV-11) |
| `container_memory_working_set_bytes` | gauge | bytes | `pod`, `container` | cAdvisor | vs `kube_pod_container_resource_limits` | Q3: OOM risk |
| `node_cpu_seconds_total`, `node_memory_*` | counter/gauge | s / bytes | `mode` | node-exporter | Utilisation % | Q3: VM sizing (DEV-14) |
| `kube_pod_container_status_restarts_total` | counter | restarts | `pod` | kube-state-metrics | `increase()` | Probe failures, OOM kills |
| `traces_spanmetrics_*`, `traces_service_graph_*` | counter/histogram | calls / s | `service`, `span_name` | Tempo metrics-generator | Service map in Grafana | Trace-derived RED metrics |

**Collection:** Prometheus scrapes `/metrics` on both apps every **15 s** (ServiceMonitor `pfd-apps` in each
app namespace). Rules are evaluated every 30 s. Retention is 7 days or 6 GB.

**Cardinality:** labels are bounded. `route` uses the route template (`/v1/devices/:id`, not the real id), and
unmatched paths collapse to `unmatched`. `reason` and `outcome` are fixed enums. **`deviceId` and `eventId` are never labels**:
with 10 devices it would be harmless, but a real fleet would create one series per device per metric. Per-device
detail lives in logs and traces instead. Current footprint: ~400 (dev, 2 pods) to ~550 (prod, 3 pods) active series per environment.

## 6. Logs (Annex II item 3)

JSON to stdout (pino), collected by the OpenTelemetry Collector (`filelog`) and stored in Loki for 7 days.
Fields: `timestamp`, `level`, `component`, `env`, `msg`, `requestId`, `trace_id`, `span_id`, `deviceId`, `eventId`,
`outcome`, `durationMs`. API keys, `DATABASE_URL` and full payloads are never logged.

Useful queries (Grafana → Explore → Loki):

```logql
# all rejections in prod, with their reason
{k8s_namespace_name="pfd-prod", service_name="ingest-api"} | json | outcome="rejected"
# follow one event across both components
{k8s_namespace_name="pfd-prod"} | json | eventId="<id>"
# everything for one request/trace
{k8s_namespace_name="pfd-prod"} | json | trace_id="<trace id>"
```

## 7. Traces (Annex II item 5)

OpenTelemetry Node SDK in both apps, sending OTLP/HTTP to the collector, then Tempo (72 h retention).
- `ingest-api`: HTTP server span → `pg` spans for the INSERT. The W3C `traceparent` is stored with the event row.
- `processor`: `process_batch` span → one `process_event` span per event, with a **span link** to the ingest
  trace (from the stored `traceparent`). That keeps the asynchronous hop traceable even though the processing
  happens later, in another process.
- Grafana: Tempo → trace → "Logs for this span" (trace_id filter in Loki); from Loki, the `trace_id` field links back to Tempo.

Sampling: 100% (always-on). At the course loads (≤ 20 events/s) this fits comfortably in the 5 GB volume. The limit would be
Tempo's local disk; the next step would be tail sampling in the collector (keep errors and slow traces).

## 8. Restoring the instrumentation (Annex II item 9)

Everything is in git. `kubectl apply -k k8s/observability` reinstalls the stack, rules and dashboard. The
deploy workflow re-applies the app ServiceMonitors. Grafana has no persistent state: datasources come from the
kube-prometheus-stack values, and dashboards come from the `pfd-dashboards` ConfigMap. The only manual step is the
`grafana-admin` Secret (`docs/runbooks/rebuild.md`). Edits made in the Grafana UI are lost on restart **by design**;
change the generator script instead.
