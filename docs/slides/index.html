02 El problema y nuestra solución

Sensores poco confiables, resultados confiables

MF
Masciel Fuentes

Lo que hace difícil el problema

DuplicadosEl sensor reenvía la misma lectura. No debe contarse dos veces.
DesordenLlegan lecturas viejas después de las nuevas. Se ordena por hora de generación.
RáfagasMiles de eventos de golpe. Ninguno confirmado se pierde.
InterrupcionesSi algo se cae, al volver se completa lo pendiente.

Nuestra solución: tres piezas

APIrecibe y valida cada evento
→
Base de datoslo guarda y funciona como fila de espera
→
Procesadortoma de la fila y genera alertas
  • La API responde "recibido" solo cuando el evento ya quedó guardado.
  • Un evento repetido se reconoce y no se guarda dos veces.
  • Si el procesador se cae, la API sigue recibiendo: los eventos esperan su turno.
Recibidose guardó y espera su turno
Duplicadoya existía: no se guarda otra vez
Rechazadodato inválido: se anota el motivo
Separar recibir de procesar es la idea central del diseño.
Masciel
  • Una organización de mantenimiento recibe temperatura, humedad y estado de sus sensores.
  • Los cuatro problemas: duplicados, desorden, ráfagas e interrupciones. Dar un ejemplo cotidiano de cada uno.
  • La solución tiene tres piezas. La clave es que recibir y procesar están separados: si el procesador falla, nada se pierde.

03 DevOps · Plataforma

Una máquina en la nube, administrada por Kubernetes

AR
Axel Renderos
1 · Entra cifradoLos sensores envían por HTTPS a una dirección pública.
2 · Se reparteNGINX recibe el tráfico y lo manda al ambiente correcto.
3 · Cada ambiente aisladodev y prod no comparten datos ni contraseñas.

Kubernetes se encarga de

  • ↻Levantar de nuevo lo que se cae
  • ⏸Sacar de circulación lo que no responde
  • ⇄Actualizar pieza por pieza, sin cortes

Dos ambientes separados

dev para probar, prod para la versión oficial. Cada uno con su propia base de datos y contraseñas.

Acceso restringido

Desde internet solo se ve la web (HTTPS). La administración entra por un túnel de Google que exige la cuenta autorizada.

Axel
  • Todo corre en una sola máquina virtual de Google Cloud con Kubernetes ligero (K3s).
  • Kubernetes recibe lo que queremos ("dos copias de la API, un procesador, una base de datos") y lo mantiene así.
  • Los sensores entran por HTTPS; NGINX recibe el tráfico y lo reparte al ambiente correcto.
  • Dos ambientes en la misma máquina: dev y prod, totalmente separados.
  • Pregunta probable: "¿qué pasa si borro un pod?" → Kubernetes crea otro; los datos viven en un disco aparte.

Objetivos medibles, alertas con criterio

BT
Benjamin Trabanino
Objetivo de disponibilidad · 7 días
99.5%

de los envíos atendidos sin fallar.

● Presupuesto de error: de cada 200 envíos, 1 puede fallar (0.5%).

Objetivo de frescura · el propio del escenario
99%

de los eventos procesados en menos de 5 segundos.

La API puede estar perfecta mientras el procesamiento va atrasado. Solo la frescura lo detecta.

4 alertas

Pruebas del curso en producción

  • ✓Ráfaga de 1,000: todos procesados
  • ✓20 por segundo, 2 min: 0 errores
  • ✓Duplicados y desorden: cálculos correctos
  • ✓Procesador apagado: 878 en espera, 0 perdidos
Benjamin
  • Indicador (SLI) = porcentaje de cosas que salieron bien. Objetivo (SLO) = el mínimo que prometemos. Presupuesto de error = lo que se permite fallar.
  • Disponibilidad 99.5% y frescura 99%. La frescura es la importante porque recibir y procesar están separados.
  • Las alertas de objetivos miden qué tan rápido se gasta el presupuesto: ignoran picos breves y se apagan rápido al corregir.
  • Pruebas: cada una se verifica comparando números antes y después con un solo comando, no con capturas.

Lo que aprendimos

  • 1El problema fue la espera: entraban más eventos de los que salían y la fila creció sin parar.
  • 2Separar funcionó: la API siguió recibiendo y no se perdió nada.
  • 3La CPU engaña: bajó durante el incidente. Hay que escalar por tamaño de la fila.
Benjamin
  • Hipótesis escrita antes: si el procesador se vuelve lento, la fila crece y las alertas lo detectan.
  • Se hizo más lento al procesador con 20 eventos por segundo entrando: bajó a 12 por segundo y la fila llegó a ~2,780.
  • Alerta de frescura a los 2 minutos; luego "fila creciendo". Volvimos a la versión anterior y la fila se vació en 51 segundos.
  • Lecciones: la espera, no la lentitud; el desacople funcionó; la CPU no refleja este tipo de falla.
  • Límite honesto: una sola máquina, una corrida, datos simulados.
